# Lessons: retiring the em dash

Source: the cleanup PR deferred from
[the local gate parity project](2026-07-30-local-gate-parity.md#deferred-with-reasons).
Role: Implementer, reviewed by the Architect.

## L1. A stated rule with no guard is a rule that is drifting

`AGENTS.md` has required a plain dash since the repository's first commits.
By the time anyone counted, there were 766 em dashes across ~114 files. Nobody
ignored the rule; it simply had no way to be noticed, and every integration
brought more.

The interesting part is *where* they came from. Almost none were written by
someone who had read `AGENTS.md` and disagreed. They arrived in bulk when the
`atlas` corpus and the `prod` module were integrated - content authored under a
different house style, moved in wholesale. An integration is the moment a
repository's writing rules are most likely to be violated and least likely to be
checked, because the review attention is on structure, licensing, and CI.

**Lesson:** a written rule with no guard should be read as an estimate of intent,
not a description of the tree. When a rule has existed unguarded for a while, do
not assume the violation count is small - measure it before deciding whether the
cleanup is a five-minute job or a project.

**Codified:** [`tools/policy/check_writing.py`](../../../tools/policy/check_writing.py),
in the `policy` workflow and in `make policy`.

## L2. Land the guard in the PR that makes the tree clean, not before

This was decided in the previous project and held up here. A guard added while
the tree is still red is a guard that fails on its author's first unrelated PR,
and the lesson people take from that is to bypass guards.

The converse discipline matters too: the cleanup PR without the guard is a PR
whose value decays from the moment it merges. Both halves in one PR, cleanup
first, guard second.

**Lesson:** the ordering is not a style preference. It determines whether the
guard is experienced as a safety net or an obstacle, and that determines whether
the next person adds one.

**Codified:** the practice is now demonstrated twice; the standing rule already
lives in [LIFECYCLE.md](../../LIFECYCLE.md#standing-rules-both-modes)
("every mechanical review finding becomes a CI guard in the same correction PR").

## L3. Not every occurrence of a character is an instance of the rule

Two of the 766 were not punctuation at all:

- `prod/app/agent_simulation_control_plane_mvp.html` uses `'—'` as a **table
  value** meaning "not applicable", rendered to an operator. Replacing it edits
  the product.
- `atlas/docs/content-guide.md` documented `license: "—"` as the marker for an
  unknown source license. A blind replace turned it into `license: " - "`, which
  is not a value at all.

A global find-and-replace would have shipped both. The second one is the more
dangerous shape, because it produces something that still parses.

**Lesson:** before a bulk rewrite, separate the character-as-punctuation cases
from the character-as-data cases. Grep for the character in quoted or delimited
positions first; those are the ones where a replacement changes meaning rather
than style.

**Codified:** the two data cases are exclusions with reasons in the guard, and
the guard carries a second check that fails when an excluded path stops
existing - so an exclusion cannot quietly become dead.

## L4. A markdown-aware rewrite has to know what a leading dash means

Three em dashes sat at the start of a line, as wrapped sentence continuations.
Replacing them in place turns each into a Markdown **list item**: the rendered
page grows a bullet where there was a sentence. The build stays green, the
schema still validates, and only a reader notices.

The transformer was written to refuse line-leading dashes and report them, which
turned a silent rendering bug into three lines of manual reflow.

**Lesson:** when a mechanical rewrite touches a structured text format, the
transformer must model the format, not just the character. The cheapest way to
do that is to make it decline the cases it cannot reason about, rather than
guess.

**Codified:** the guard's failure message says so explicitly - *"A line-LEADING
em dash needs reflowing rather than replacing"* - so the next person meets the
hazard at the moment it applies.

## L5. Verify a prose change by reading the prose

The gates all passed on the first run: `astro check` clean, 50 pages built, the
corpus schema valid, 61 tests green. None of that would have caught a stray
bullet, a doubled space, or a placeholder turned into `" - "`. A build proves the
page compiles, not that it reads.

The three real defects in this change were found by reading rendered output: two
by inspecting the reflowed sentences on the running site, one by diffing added
lines for doubled spaces around a dash.

**Lesson:** for a change whose entire surface is prose, the passing build is the
weakest evidence available. Read the rendered result, and diff the change for the
artifacts your own transformer could have introduced.

**Codified:** no guard - this is a review discipline. The evidence file records
the rendered read-back for all three reflowed pages and the site-wide sweep that
found zero em dashes across 49 built pages.

## L6. A rule about prose has to know the difference between using a character and naming it

The first version of the guard was a shell script grepping whole files for the
character. It went green on the cleaned tree, and then failed on this project's
own article, lesson, evidence file, and Lab Notes entry: eleven violations, every
one of them the em dash being *quoted* - inside `inline code` or a fenced block -
to show a reader the hazard being described.

The guard, as first written, made it impossible to document the rule it enforced.
The article explaining why a line-leading em dash becomes a list item cannot
demonstrate that without printing the character.

That is the same distinction as L3, arriving from the other direction. L3 was
about the *tree*: some occurrences are data, not punctuation, so do not rewrite
them. L6 is about the *guard*: some occurrences are quotation, not punctuation,
so do not flag them. Both are the observation that a character has no meaning
until you know its context.

**Lesson:** when a guard enforces a writing rule, decide early whether it is
checking characters or checking prose. Checking characters is one grep and is
wrong the first time someone documents the rule. Checking prose costs a real
parser - here, masking fenced blocks and inline code spans while preserving line
numbers - and is the only version that survives contact with its own
documentation.

**Codified:** [`tools/policy/check_writing.py`](../../../tools/policy/check_writing.py)
masks fences and code spans in Markdown, and prose-checks non-Markdown files
whole, since an em dash in a comment is ordinary writing. Exercised in seven
directions, including a prose dash *after* a closed fence to prove the masking
does not swallow the rest of the file, and to prove reported line numbers stay
correct.

## Deferred, with reasons

- **En dashes: 103 across 36 files.** `AGENTS.md` names the em dash
  specifically, and most of these are numeric ranges (`5-15 min`), where the en
  dash is correct typography rather than a violation. Widening the writing rule
  is a decision for the Architect; if it is widened, the same
  cleanup-then-guard ordering applies.
- **Curly quotes and apostrophes** are untouched for the same reason: no stated
  rule covers them.
